# Synthetic Data Generation

This module generates synthetic documents for the PII classification pipeline.

The generator creates controlled document scenarios with known ground-truth labels and entity metadata. Structured document content is generated deterministically, while selected free-text content is enriched through an LLM.

The generated dataset follows the same 44-column schema used by the classification pipeline.

## Dataset design

The default configuration generates:

- 14 document scenarios
- 100 documents per scenario
- 1,400 documents in total
- 12% PII-positive documents
- 88% PII-negative documents
- 70% training data
- 15% validation data
- 15% test data
- English and German documents

The scenario planner controls class balance, dataset splits, languages, variants, entity combinations, and generation seeds before document text is generated.

The currently supported scenarios are:

- `contract`
- `customer_support`
- `employee_record`
- `expense_report`
- `general_document`
- `incident_report`
- `internal_email`
- `invoice`
- `it_access_request`
- `medical_record`
- `meeting_notes`
- `passport_record`
- `supplier_onboarding`
- `training_evaluation`

## Generation approach

Generation separates controlled metadata and structured values from LLM-generated text.

### Deterministic generation

The planner and Faker-based generator create:

- document scenarios and variants
- PII-positive and PII-negative assignments
- train, validation, and test splits
- languages
- entity combinations
- structured document fields
- fictional PII values
- deterministic generation seeds

Using the same configuration, seed, and dependency versions reproduces the same deterministic generation plan.

### LLM enrichment

Production generation enables LLM enrichment by default.

There are two LLM generation modes.

**Field-level enrichment**

Structured documents retain their controlled layout and values. Only designated free-text fields are generated by the LLM.

This applies to:

- `contract`
- `customer_support`
- `employee_record`
- `expense_report`
- `incident_report`
- `invoice`
- `it_access_request`
- `medical_record`
- `meeting_notes`
- `supplier_onboarding`
- `training_evaluation`

**Full-document generation**

Free-form scenarios are rewritten as complete documents while preserving the controlled values required by the generation plan.

This applies to:

- `general_document`
- `internal_email`

`passport_record` remains fully structured and does not require LLM enrichment.

LLM output is validated before it is accepted. The validation protects required values and rejects unexpected identifiers introduced by the model. If valid LLM output cannot be produced, the generator falls back to the controlled Faker/archetype representation and records the fallback in the generation metadata.

## Output files

Generation produces two CSV files.

### Dataset

The dataset contains the 44 columns expected by the classification pipeline, including:

- document identifiers and metadata
- `full_text`
- ground-truth PII labels
- entity flags and counts
- scenario and language information
- recommended dataset split
- generation metadata

### Manifest

The manifest stores generation metadata that is useful for reproducibility and auditing but should not be used as model input.

It contains:

- `document_id`
- `scenario_type`
- `variant`
- `language`
- `contains_personal_data`
- `entity_types`
- `recommended_split`
- `difficulty`
- `edge_case`
- `challenge_category`
- `scenario_seed`
- `row_seed`

Dataset and manifest rows align one-to-one through `document_id`.

## Generate a dataset

Run generation from the repository root:

```bash
python -m classification.data_generation.generate
```

The default run generates 100 documents for each of the 14 scenarios:

```text
1,400 documents
```

LLM enrichment is enabled by the generation CLI.

The output filename is derived from the total dataset size:

```text
synthetic_dataset_1400.csv
synthetic_dataset_1400_manifest.csv
```

This makes differently sized generations separate artifacts rather than version-numbered datasets.

To generate a larger dataset:

```bash
python -m classification.data_generation.generate \
    --documents-per-scenario 200
```

This produces:

```text
synthetic_dataset_2800.csv
synthetic_dataset_2800_manifest.csv
```

A custom dataset filename can also be supplied:

```bash
python -m classification.data_generation.generate \
    --documents-per-scenario 100 \
    --output custom_dataset.csv
```

The corresponding manifest filename is derived automatically.

### Generation arguments

```text
--documents-per-scenario
    Number of documents generated for each scenario.
    Default: 100.

--seed
    Base seed used for deterministic planning.
    Default: 42.

--output
    Optional dataset filename.
    If omitted, the filename is derived from the total dataset size.
```

The current planner requires at least 38 documents per scenario so that every train, validation, and test split contains both positive and negative examples.

## Audit a generated dataset

Every generated dataset should be audited together with its manifest before it is used for training or evaluation.

For the default dataset:

```bash
python -m classification.data_generation.audit \
    classification/data_generation/output/synthetic_dataset_1400.csv \
    --manifest classification/data_generation/output/synthetic_dataset_1400_manifest.csv
```

The audit checks include:

- dataset schema and column order
- manifest schema and alignment
- unique document IDs
- missing document text
- unexpected duplicate documents
- supported scenarios, languages, and splits
- consistency between class labels and entity metadata
- primary PII type and entity counts
- negative-document identifier leakage
- LLM generation fallbacks
- entity coverage
- scenario coverage across splits
- positive and negative class coverage across splits

Exact duplicates caused by intentional blank document templates are distinguished from unexpected duplicate documents.

Audit reports are written to:

```text
classification/data_generation/output/audits/
```

Both text and JSON reports are created with timestamps, so repeated audits do not overwrite previous reports.

### Strict audit mode

The audit can also be run in strict mode:

```bash
python -m classification.data_generation.audit \
    classification/data_generation/output/synthetic_dataset_1400.csv \
    --manifest classification/data_generation/output/synthetic_dataset_1400_manifest.csv \
    --strict
```

Strict mode treats warnings as a failed audit.

## Module structure

```text
classification/data_generation/
├── archetypes.py
├── audit.py
├── config.py
├── generate.py
├── generation_values.py
├── generator.py
├── llm_render.py
├── models.py
├── planner.py
├── records.py
├── README.md
└── output/
```

`config.py` contains shared generation configuration and the canonical dataset schema.

`archetypes.py` defines the supported document structures.

`planner.py` creates deterministic generation requests, including class, split, language, variant, and entity assignments.

`generation_values.py` contains controlled structured and scenario-specific values.

`generator.py` builds field values, assigns synthetic entities, renders documents, and assembles the dataset and manifest.

`llm_render.py` handles constrained field-level and full-document LLM generation and validates model output.

`records.py` serializes generated documents into the canonical dataset schema.

`generate.py` provides the production generation CLI.

`audit.py` validates generated datasets and manifests and produces reusable audit reports.

## Reproducibility

The generation plan is seed-controlled. The default base seed is:

```text
42
```

Scenario and row seeds are derived deterministically from this base seed and are recorded in the manifest.

LLM-generated wording is not expected to be byte-for-byte reproducible across separate runs because model responses may vary. The controlled generation plan, ground-truth assignments, structured values, and manifest provide the reproducible basis of the dataset.

For experiments that require deterministic text generation without LLM enrichment, the lower-level generator functions can be called with `use_llm=False`.

## Recommended workflow

For a training-ready generation:

```text
1. Generate the dataset and manifest.
2. Run the audit with the matching manifest.
3. Require the audit to pass before using the dataset.
4. Inspect generation metadata and LLM fallback counts.
5. Review representative documents across scenarios, languages, classes, and variants.
6. Use the recommended train, validation, and test splits for downstream evaluation.
```

Generated files are artifacts of a particular generation run. Code and configuration changes should be reviewed separately from generated output before committing a new dataset.
